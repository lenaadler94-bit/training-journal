# project-workflow — навык работы с репозиторием

Ты помогаешь работать с репозиторием тренировочного журнала в Obsidian-vault. Применяешь общие принципы из `CLAUDE.md`: фиксируешь только то, что названо, не выдумываешь данные, перед значимыми действиями показываешь план и ждёшь подтверждения.

## Структура проекта

```
.
├── CLAUDE.md                    # инструкции ассистенту (основные принципы)
├── README.md                    # описание проекта для GitHub
├── .gitignore
├── Cold training/               # холодовой тренинг
├── functional/                  # функциональные тренировки
├── running/                     # бег (включая СБУ/ОФП)
├── yoga/                        # йога
├── swimming/                    # плавание
├── other/                       # прочие направления
├── reports/                     # сводные отчёты по периодам
├── images/                      # скриншоты для README
├── tmp/                         # временные файлы (не коммитится)
└── .claude/
    ├── agents/training-analyst.md
    └── skills/
        ├── cold-training note/
        ├── functional note/
        ├── running note/
        ├── swimming note/
        ├── yoga note/
        └── project-workflow/     # этот навык
```

**Имя файла заметки:** `YYYY-MM-DD_<тип>.md`. Если в один день несколько тренировок одного типа — суффикс `-2`, `-3` и т.д.

## Когда вызывается

- Просьба проверить структуру/состояние проекта.
- Просьба обновить README.
- Просьба проверить ошибки в vault или в skills.
- Просьба подготовить изменения к коммиту.

Публикация на GitHub (`git push`, создание репозитория) — **отдельная задача**, требует явного запроса и подтверждения. Этот навык не запускает её сам.

## Внесение изменений

1. **Понять, что именно меняется** — заметка, skill, агент, README, .gitignore. Если неоднозначно — спросить.
2. **Соблюдать принципы из `CLAUDE.md`:**
   - Не добавлять параметры, цифры, оценки, которых не назвал пользователь.
   - Пустые поля в заметках оставлять пустыми.
   - Не удалять и не переименовывать файлы без явного разрешения.
   - Не выходить за пределы рабочей директории.
3. **Для нового скилла/агента** — показать структуру и расположение, дождаться подтверждения, затем создать.
4. **После правок** — коротко перечислить изменённые файлы. Отдельный отчёт не нужен, если не просят.

## Обновление README

Когда обновлять:
- Изменилась структура vault (добавили/удалили папку типа тренировки).
- Добавился новый skill или агент.
- Изменились принципы работы или шаблон записи.
- Изменилось содержимое `images/`.

Как обновлять:
- Синхронизировать разделы с фактическим состоянием vault — без выдумывания того, чего в проекте нет.
- Пути к изображениям — кодировать пробелы как `%20`. Каждое изображение отделять пустой строкой, иначе markdown склеит их в один абзац.
- Не вставлять изображения, которых нет в `images/`.
- Сохранять тон и структуру существующего README.

## Проверка ошибок

Что контролировать (без выдумывания проблем — только то, что реально обнаружено):

**Заметки:**
- Имя файла соответствует шаблону `YYYY-MM-DD_<тип>.md` (или с суффиксом `-N`).
- Тип в имени файла совпадает с папкой, где лежит файл.
- Frontmatter корректен (если есть), нет битого YAML.
- Поля, которых пользователь не назвал, — пустые, а не заполненные значениями по умолчанию.
- Нет дубликатов записей за одну дату без суффикса.

**Skills и агенты:**
- У каждого скилла есть `name`, `description`, `trigger` в frontmatter.
- Имя скилла соответствует имени папки.
- Нет ссылок на несуществующие файлы/папки.
- Шаблоны заметок внутри скиллов соответствуют общему шаблону из `CLAUDE.md`.

**README:**
- Пути к изображениям кодированы (`%20` вместо пробелов).
- Каждое изображение в отдельном абзаце.
- Структура vault в README соответствует фактической структуре.
- Нет ссылок на файлы, которых нет в репозитории.

**Git:**
- `tmp/`, `.obsidian/`, служебные файлы не должны попасть в коммит (см. `.gitignore`).
- Нет чувствительных файлов (токены, ключи, личные данные) в staged.

Формат результата проверки — короткий список найденных проблем с путями файлов. Если проблем нет — так и сказать.

## Подготовка изменений к коммиту

Этот навык **не делает** `git push` и не создаёт репозиториев. Он только готовит:

1. `git status` — показать, что изменилось.
2. Проверить, нет ли в staged чувствительных файлов (токены, `.env`, ключи, личные данные). Если есть — предупредить, не добавлять.
3. Не использовать `git add -A` / `git add .` — добавлять конкретные файлы по именам.
4. Подготовить осмысленное сообщение коммита (что и зачем, не «update»).
5. Если в изменениях есть файлы из `.gitignore` или служебные — явно спросить, включать ли их.
6. Сам коммит (`git commit`) — выполнять только после явного подтверждения пользователя. Push — отдельным запросом.

## Чего не делать

- Не запускать `git push`, `git reset --hard`, `git force push`, `gh repo create` без отдельного явного запроса.
- Не удалять и не переименовывать файлы без явного разрешения.
- Не выходить за пределы рабочей директории проекта.
- Не выдумывать данные, цифры, оценки в заметках и README.
- Не добавлять файлы `git add -A` — только по именам.
- Не отправлять сообщения во внешние системы.
- Не пропускать чувствительные файлы в коммит.

## Порядок действий при вызове

1. Уточнить, что именно нужно: проверка / обновление README / правки / подготовка к коммиту.
2. Выполнить соответствующий раздел выше.
3. Перед значимыми действиями (правки, коммит, создание файлов) — показать план и дождаться подтверждения.
4. После — коротко перечислить изменённые файлы.
